## 1. 项目概览

### 1.1 主要结果

| 项目                | 结果                                                                     |
| ----------------- | ---------------------------------------------------------------------- |
| 交付配置              | `lr = 2e-5` · `batch_size = 16` · `dropout = 0.1` · `max_length = 128` |
| **Test Accuracy** | **83.08% ± 0.28%**（3 seeds: 42 / 66 / 99）                              |
| **Test Macro-F1** | **81.98% ± 0.15%**                                                     |
| 验收线               | Acc ≥ 83%，余量 0.08 pp（约 0.9 条样本）                                        |
| 实验规模              | 7 组唯一配置 × 3 seeds = **21 次完整训练**                                       |
| 训练成本              | 单 seed 约 2–4 min，全量约 1 h（RTX 3070 Ti Laptop, 8 GB）                     |
| 记录方式              | SwanLab 全程记录，`swanlog/` 下 21 个 run 可离线解析                               |

### 1.2 主要工作

- **单变量消融**：Dropout（0.1 / 0.2 / 0.3 / 0.4）→ 学习率（1e-5 / 2e-5 / 3e-5）→ Batch Size（8 / 16），每次只动一个参数，其余锁定。
- **多种子重复**：每组 3 个种子，报告 `mean ± std` 与 95% 置信区间；差距小于置信区间时按统计等价处理。
- **数据审计**：训练前统计三份数据的重复标题、标签冲突与长尾分布，并估计其对指标的影响。
- **可复现**：固定数据文件、固定 seeds、`cudnn.deterministic=True`，超参写入 `configs/params.json`，单条命令完成 3 个种子的训练。

## 2. 数据集

### 2.1 基本情况

来源为今日头条文本分类数据集（TNEWS）切片。每行 5 个字段、以 `_!_` 分隔，第 2 字段为类别 `code`，第 4 字段为新闻标题。**模型只使用标题**，共 15 个类别（标签 `100–116`，实际缺少 `105`、`111`）。

| 划分  | 文件             |  样本数 |
| --- | -------------- | ---: |
| 训练集 | `train_3k.txt` | 3000 |
| 验证集 | `dev_1k.txt`   | 1000 |
| 测试集 | `test_1k.txt`  | 1064 |

### 2.2 数据审计

对三份数据做标题级比对：

| 检查项               | 数量 | 影响                          |
| ----------------- | -: | --------------------------- |
| train 与 test 重复标题 | 31 | 约 2.9% 的测试样本在训练中出现过，指标略微偏乐观 |
| train 与 dev 重复标题  | 28 | 早停与选 checkpoint 的验证信号略偏乐观   |
| dev 与 test 重复标题   | 18 | 选参与评估共享样本，削弱独立性             |
| train 内部重复标题      | 63 | 等效训练样本量低于 3000              |
| 同名不同标签（跨划分冲突）     |  3 | 标注噪声，模型无法全部判对               |

本实验未修改原始数据，上述重叠会使指标偏高。

## 3. 方法

### 3.1 模型

```python
pooled = BertModel.from_pretrained("bert-base-chinese")(...).pooler_output   # [B, 768]
logits = Linear(768, 15)(Dropout(p)(pooled))                                # [B, 15]
loss   = CrossEntropyLoss(logits, labels)
```

- 取 **`pooler_output`**（`[CLS]` 经 `Linear + Tanh` 后的句子级向量），而非对所有 token 做 mean pooling。标题短、关键信息集中，`[CLS]` 在预训练阶段已被训练为聚合句义；实现上也不必处理 padding mask 的加权平均。这一选择基于实现成本与常见实践，本文未对 pooling 方式做对照实验。
- 分类头只有一层线性层。3000 条样本难以支撑更深的头部，增加层数会加快过拟合。

### 3.2 训练配方

| 组件         | 设置                                 | 说明                                  |
| ---------- | ---------------------------------- | ----------------------------------- |
| 优化器        | AdamW（`weight_decay = 0`）          | 代码仅设置学习率，未启用权重衰减；本实验的正则项只来自 dropout |
| 学习率调度      | Linear warmup (10%) + linear decay | 前 188 步线性升温，避免初期大梯度破坏预训练权重          |
| 梯度裁剪       | `max_norm = 1.0`                   | 只缩放范数、不改变方向，抑制梯度爆炸                  |
| Batch size | 16                                 | 8 GB 显存上实测稳定；bs=32 未测（显存不足）         |
| 最大轮数       | 10                                 | 配合早停，21 次运行平均 8.2 轮（5–10 轮）         |
| 早停         | `patience = 3`                     | 监控 dev Acc，连续 3 轮未提升即停止             |
| 模型选择       | dev Acc 最高的 checkpoint             | 测试集不参与 run 内的 checkpoint 选择         |
| 随机种子       | 42 / 66 / 99                       | 覆盖 3 次独立初始化与数据打乱                    |

## 4. 实验设计

### 4.1 研究问题

| 编号  | 问题                        | 对应实验 |
| --- | ------------------------- | ---- |
| RQ1 | Dropout 如何影响过拟合边界与长尾类表现？  | G1   |
| RQ2 | 学习率如何影响收敛速度与训练稳定性？        | G2   |
| RQ3 | Batch size 如何影响梯度噪声与最终精度？ | G3   |

### 4.2 固定参数

```json
{
  "model_name": "bert-base-chinese",
  "max_length": 128,
  "max_epochs": 10,
  "patience": 3,
  "seed_list": [42, 66, 99],
  "max_norm": 1.0,
  "warmup_ratio": 0.1
}
```

### 4.3 实验矩阵：坐标下降而非全网格

| 组  | 维度         | 取值                | 锚点                |   runs |
| -- | ---------- | ----------------- | ----------------- | -----: |
| G0 | 初始基线       | `2e-5 / 16 / 0.2` | —                 |      3 |
| G1 | Dropout    | `0.1 / 0.3 / 0.4` | `2e-5 / 16 / 0.2` |      9 |
| G2 | 学习率        | `1e-5 / 3e-5`     | `2e-5 / 16 / 0.1` |      6 |
| G3 | Batch size | `8`               | `2e-5 / 16 / 0.1` |      3 |
|    |            |                   | **合计**            | **21** |

先固定 `lr=2e-5, bs=16` 扫 dropout（G1），确定 0.1 为最优后，再以 `2e-5 / 16 / 0.1` 为锚点扫学习率（G2）与 batch size（G3）。

两个未纳入的点：

- **`bs=32`**：未实测。按显存估算 OOM 风险较高（`max_length=128` 下 batch 翻倍、激活显存翻倍）；强行缩短序列又会引入「截断长度」这一额外变量。若需更大 batch，可用梯度累积（bs=16 × 累积 2 步）模拟。
- **`lr=5e-5`**：3e-5 已出现明显震荡，继续加大只会放大不稳定。

### 4.4 评估协议

| 阶段                     | 使用数据             | 决策依据            |
| ---------------------- | ---------------- | --------------- |
| run 内训练                | train            | —               |
| run 内早停 / 选 checkpoint | dev Acc          | 每个 run 独立保存最优权重 |
| 跨配置排序                  | test（3 seeds 均值） | 验收指标为 test Acc  |

每个 run 内部用 dev 做早停与模型选择，跨配置比较使用 3 个种子的 test 均值。dev 仅 1000 条，7 组配置的 dev 均值集中在 0.66 pp 的区间内，与种子噪声同量级，不足以区分组间差异。test 指标在训练结束后单独评估，由 `main.py` 汇总打印；SwanLab 只记录 dev 曲线与训练损失。

从 Acc 口径来看：7 组中有 6 组的 Test Acc 低于 Dev Acc，平均落差为 −0.36 pp；仅配置 2 的 Test Acc 略高于 Dev Acc（+0.12 pp）。其中落差最大的两组是 `lr=3e-5`（−1.20 pp）与 `bs=8`（−0.57 pp），恰好也是种子间指标标准差最大的两组。这符合早停机制带来的规律：checkpoint 基于验证集 Acc 筛选，验证集 Acc 天然存在乐观偏差；尤其是`bs=8`这一组，验证集 Acc 在全部配置里最高（83.53%），但测试集 Acc 明显回落至 82.96%，该泛化落差也可以在 SwanLab 训练曲线上定位到对应的最优轮次。

从 Macro-F1 口径来看，正负方向并不统一：配置 1、3、4、5 的\(\Delta\text{F1}\)为小幅正值，也就是测试集 Macro-F1 略高于验证集；配置 2、6、7 为负值，7 组平均\(\Delta\text{F1}=-0.26\ \text{pp}\)。
Test Macro-F1 高于 Dev Macro-F1 容易被视作反常现象，这里从三点解释：

1. **差值幅度很小，属于抽样随机波动**。测试集共 1064 条样本，单条样本对应约 0.094 pp，本组最大正向差值 + 0.21 pp 仅等价于 2 条样本预测结果发生变化，该量级无法和数据集抽样噪声区分开。
2. **早停监控目标是 Dev Acc，不是 Dev Macro-F1**。我们挑选权重时只优化、筛选 Acc，没有对 Dev Macro-F1 做择优。“测试集指标一定低于验证集” 这个预期，只适用于作为筛选依据的 Acc；Dev Macro-F1 不参与 checkpoint 选择，因此不存在系统性高于测试集 Macro-F1 的必然性。
3. **Acc 和 Macro-F1 在验证、测试集上的差距本身不一致**。Acc 和 Macro-F1 之间存在固有 gap：验证集上`Acc − Macro-F1`差值区间为 1.20–3.21 pp，测试集上为 1.10–2.65 pp，验证集的 Acc-F1 间隙整体略宽。\(\Delta\text{F1}\)和\(\Delta\text{Acc}\)不是独立的两个信号，二者满足恒等关系：

综合来看，验证集与测试集指标落差整体控制在 1.2 pp 以内，没有出现严重过拟合验证集的证据。其中配置 6、7 的指标衰减幅度显著更大，同时伴随很高的种子间波动，属于真实的泛化性能退化；而配置 1、3、4、5 的正向\(\Delta\text{F1}\)仅为抽样噪声，不能理解为测试集分类难度低于验证集。

### 5.2 消融分析

0.1 与 0.2 的差别落在 F1 上。两者 Acc 相差 0.03 pp（约 0.3 条样本），Macro-F1 相差 0.48 pp，F1 标准差相差 1.6 倍。Acc 等价时，0.1 的 F1 更高、波动更小。继续增大 dropout，降幅不再对称。0.1 增至 0.4，Acc 下降 0.50 pp，Macro-F1 下降 2.05 pp；F1 标准差由 0.15 扩大到 2.14，0.3 组达到 2.33，约为 0.1 组的 15.5 倍。多数类仍能维持、稀有类先失效，是这一模式的典型特征。

两个离群 run 给出了机制上的说明。dp=0.3, seed 99 在其最优 epoch 上 Acc 为 82.50%、Macro-F1 仅 76.54%，两者相差 5.96 pp；dp=0.4, seed 42 为 Acc 83.00%、Macro-F1 76.40%。两个模型的 Accuracy 都在正常区间，Macro-F1 已明显偏离。按 15 类 macro 平均折算，5.96 pp 约合 89 个 F1 百分点；若集中于 3 个稀有类，相当于每类下降约 30 点（0.6 → 0.3），与类 114 在验证集中仅有 14 条样本的分布相符。

继续增大 dropout 未带来更好的泛化。0.4 的末轮 train loss（0.071）是 0.1（0.029）的 2.4 倍，最优 epoch 也由 6.7 提前至 4.0。但这一差异不能直接读作欠拟合：dropout 越强，训练损失本身越高；同组中 0.4 的末轮 dev loss（0.909）反而是四组最低，dev Acc（83.10）与 0.1（83.17）基本持平。退化集中在 Macro-F1（79.93）与种子间标准差（2.14）上，说明被抑制的是稀有类的判别信号，而非整体拟合能力。

结论：dropout = 0.1。在 Acc 持平的前提下，它给出更高的 Macro-F1 与更小的波动。

更新次数增加，未带来更好的特征。末轮 epoch 级 train loss 的 3 种子均值为 0.024（bs=8）与 0.029（bs=16），bs=8 反而低 0.005；同期末轮 dev loss 为 1.135 与 0.949，高 0.19。训练损失更低而验证误差更高，说明多出的更新主要用于拟合批内 8 条样本的噪声。step % 10 == 0 的采样记录也支持这一点：bs=8 在第 4–7 轮的批内最大值为 1.07 / 1.36 / 0.92 / 0.96，而 bs=16 自第 4 轮起未超过 0.46。

需要说明一处混杂：bs=8 同时把 warmup 步数（188 → 375）与调度总步数（1880 → 3750）翻倍，因此上述波动不能完全归因于批大小。严格的对照是 bs=8, max_epochs=5（总步数与基线一致），这一组尚未运行。

结论：bs=16。 在 8 GB 显存与 3000 条样本的约束下，将 batch size 减半只得到更频繁的更新和更大的方差，未提高精度上限。


### 5.3 显著性与稳定性

配置之间的差异能否成立，取决于测量精度。以下先界定测量分辨率。

- 测试集 1064 条，**1 条 = 0.094 pp**。主结果表中 0.12–0.37 pp 的差距相当于 **1–4 条样本**。
- 3 个种子下 95% CI 半宽 = `2.485 × std`：交付配置 **±0.70 pp**，bs=8 **±1.74 pp**，lr=3e-5 **±3.83 pp**。
- 要把 CI 半宽压到 0.3 pp（约 3 条样本），按实测 std=0.28 需 **6 个种子**；压到 0.15 pp 需 **16 个**。3 个种子能够分辨的最小差异约 0.7 pp，这是后续所有比较的分辨率下限。

不同配置的不稳定表现落在不同维度上。下表把 21 条曲线归纳为同一组指标：

|    配置 (lr/bs/dp)    | dev loss 谷底轮次 | 谷底后斜率 (/轮) | 末轮 dev loss | Dev Acc 逐轮抖动 (pp) | Dev Acc 种子极差 (pp) | Dev F1 种子极差 (pp) |
| :-----------------: | :-----------: | :--------: | :---------: | :---------------: | :---------------: | :--------------: |
| **2e-5 / 16 / 0.1** |      3.0      |    0.047   |    0.949    |        0.64       |      **0.1**      |      **0.8**     |
|   2e-5 / 16 / 0.2   |      3.0      |    0.056   |    0.973    |        0.78       |        0.5        |        0.9       |
|   2e-5 / 16 / 0.3   |      3.0      |    0.051   |    0.947    |        0.72       |        1.1        |      **5.8**     |
|   2e-5 / 16 / 0.4   |      3.0      |    0.061   |    0.909    |        0.99       |        0.2        |      **5.4**     |

口径：谷底轮次与斜率为每个 run 的 dev loss 序列自谷底轮至末轮线性拟合后取 3 种子均值；逐轮抖动是去掉第 1 轮爬升后，相邻轮 dev Acc 变化量的绝对值均值；种子极差是 3 个种子在 dev 上最优指标的 `max − min`。表中全部指标均为 dev，原始记录来自 `swanlog/`。

表中的指标指向三种不同的不稳定形态。

- **bs=8：训练过程内部抖动最大**（0.99 pp/轮，与 dp=0.4 并列），谷底最早（2.0 轮）、回升最陡（0.067/轮）。波动发生在一次训练之内，可由曲线直接观察。
- **lr=3e-5：曲线内抖动最小**（0.58 pp/轮），但 **Acc 种子极差为全部配置中最大**（1.5 pp），F1 极差 2.5 pp。三次训练停在不同位置：seed 42 停在 82.10%，seed 66 达到 83.60%。只看一条曲线会低估它的波动，需要并排 3 个种子。
- **dp=0.4：Acc 极差仅 0.2 pp，F1 极差 5.4 pp**。`seed 42` 的 Acc 83.00% 处于正常区间，Macro-F1 只有 76.40%，此时只有一个指标出现异常，单看 Accuracy 无法发现。

据此，配置 1、2、5 在 Acc 上的差异（最大 0.03 pp，约 0.3 条样本）不构成差别，三者在 Acc 上统计等价。交付配置的选择依据在另外两项：**Macro-F1 最高**（81.98，比配置 5 高 0.37、比配置 2 高 0.48），且**两项标准差同时最小**（0.28 / 0.15）。配置 6（lr=3e-5）被排除，主要原因不是均值低 1.31 pp，而是 **1.54 的标准差**：三个种子的结果分散，可复现性差。

交付配置在 dev 上的两项种子极差均为最小（Acc 0.1、F1 0.8），逐轮抖动 0.64 略高于 lr=3e-5 的 0.58。因此报告「±0.28，稳定」这类结论时必须注明所指维度：同一个 ± 号可能表示曲线内噪声、种子间漂移，也可能只出现在 Macro-F1 上。

**边界说明**：83.08% 比 83% 验收线高 0.08 pp，约 0.9 条样本。因此本文不把「超过 83%」作为强结论，可保证的是「稳定在 83% 附近、种子间标准差 < 0.3 pp」。若需要更大余量，应扩充种子数并清洗重复数据。

#### 5.4.1 验证损失与准确率的走势差异

下表统计 `dp=0.1` 组的三个种子（图 5 中仅绘出 seed 42 一条）：

|  seed  | dev loss 最低点 | 该轮 dev Acc | 最优轮（按 Acc） | 该轮 dev loss |     Acc 增益 |
| :----: | :----------: | :--------: | :--------: | :---------: | -----------: |
|   42   |  0.673 @ ep3 |   82.20%   |     ep7    |    0.868    |     +1.00 pp |
|   66   |  0.673 @ ep3 |   81.80%   |     ep9    |    0.946    |     +1.40 pp |
|   99   |  0.695 @ ep3 |   82.30%   |     ep4    |    0.739    |     +0.80 pp |
| **均值** |   **0.680**  | **82.10%** |      —     |    0.851    | **+1.07 pp** |

三个种子的 dev loss 最低点全部落在第 3 轮（21 个 run 合计，谷底均在 **第 2–4 轮**），此后整体单边上行（seed 42 在第 7 轮有一次 0.878 → 0.868 的回落），至末轮平均回升 **39%**。同期 dev Acc 由谷底轮的 82.10% 升至各 seed 最优轮的 **83.17%**。即模型的验证误差在第 3 轮之后开始增大，但分类结果仍在改善。

两者衡量的对象不同：交叉熵是正确类概率的对数似然，对置信度敏感；Acc 只判断 argmax 是否命中。训练后期，模型在训练分布上继续降低损失，但在验证集上将概率质量向多数类集中：易分样本的正确类概率进一步提高，难分样本（多为稀有类）的正确类概率被压低。交叉熵对低概率的惩罚远大于对高概率的奖励，后者的损失足以抵消前者的收益，dev loss 因而上升；这些样本的 argmax 大多尚未翻转，Acc 得以维持甚至小幅上升。这一现象属于过拟合在概率层面的表现，而非校准改善。图 5 上排的后两格对应这一过程：epoch 级 train loss 保持在低位（末轮 0.014–0.053），dev loss 自第 3 轮起持续上升。

**这直接决定了 checkpoint 的选择口径**：若按 dev loss 最低点保存，得到的是第 3 轮的权重，dev Acc 为 82.10%，比实际交付的 83.17% 低 1.07 pp，约为主结果表中最大 Acc 落差（1.31 pp）的 82%。

方向比幅度更稳定：21 个 run 中 **18 个**的 P 高于 R，符号检验 p ≈ 0.0015。按配置平均，缺口从 **+0.34 pp**（dp=0.4）到 **+2.37 pp**（lr=1e-5）不等。三个例外（dp=0.3 / dp=0.4 / lr=3e-5 各一个种子，最大 −1.13 pp）全部出现在缺口最小的三个配置中（均值 +1.17 / +0.34 / +0.53 pp），与种子噪声同量级。

幅度在种子之间同样存在差异：基线三个种子分别为 2.91 / 1.69 / 0.85 pp。缺口大小受初始化与数据顺序影响，因此**可下的结论仅限于方向**：模型在稀有类上系统性偏保守，缺口并不固定为 1.8 pp。

缺口持续收窄，说明 Recall 在后半程提升更快，这也限制了结论强度：模型在训练初期即偏向保守，训练过程只是将这一偏差由明显收窄至轻微。这与长尾分布对应：类 114 只有 40 条训练样本，对交叉熵的梯度贡献不足总体的 1.5%，模型倾向于将其并入相近的多数类，而不愿为证据不足的样本承担 FP 风险。

这也解释了 dropout ≥ 0.3 时 Macro-F1 的下降：正则增强后，稀有类本就微弱的判别信号首先被抑制，Recall 下降，F1 随之下降。**下一步的优先项是稀有类加权**（class weight / Focal Loss / 分层采样），而非继续调整超参数。按 P≈82.2、R≈80.8 处 `∂F1/∂R ≈ 0.51` 折算，R 补齐 1.8 pp 且 P 不降时，Macro-F1 上限约为 **+0.9 pp**；实际必然付出部分 P 的代价，因此这是上限而非预期值。

#### 5.4.3 micro 指标与 Accuracy 的一致性

单标签多分类中，micro-P = micro-R = micro-F1 = Accuracy 是**恒等式**：每个样本只属于一个类，各类 TP / FP / FN 求和后分子分母相同。图 6 中 micro-P、micro-R、micro-F1 三个子图的曲线与 dev Acc 重合，21 个 run 逐点的最大偏离为 **6 × 10⁻⁸**，与 `utils.evaluate` 分母中 `1e-8` 平滑项的量级一致，属于浮点误差。

这也是一次评估代码的自检：`utils.evaluate` 中的 P/R/F1 由逐类 TP / FP / FN 手工累加得到，若某一类的分母算错、或 macro 的类别数取错，micro 与 Acc 会立即不一致。当前结果一致，说明逐类统计与汇总逻辑正确，主结果表中的 macro 指标可信。

| 泛化一致性 | **dev 与 test 的差 ≤ 1.2 pp**，无过拟合证据 | ΔAcc 6/7 为负、均值 −0.36 pp；ΔF1 4/7 为正但 ≤ +0.21 pp（约 2 条样本），均值 −0.26 pp             |
| 总体       | **2e-5 / 16 / 0.1**                      | Test Acc 83.08% ± 0.28%，Macro-F1 81.98% ± 0.15%                                                  |


综合来看，在小数据、长尾分布与 8 GB 显存三项约束下，温和正则、中等学习率与中等 batch size 的组合能够同时兼顾 Acc、Macro-F1 与方差。

## 6. 复现指南

### 6.1 环境

```bash
conda create -n dl python=3.10 -y
conda activate dl
pip install -r requirements.txt
```

|      依赖       |  版本  |
| --------------- | ------ |
| Python          | 3.10   |
| torch           | 2.5.1  |
| transformers    | 4.45.2 |
| tokenizers      | 0.20.3 |
| huggingface_hub | 0.36.2 |
| numpy           | 2.0.1  |
| tqdm            | 4.70.1 |
| swanlab         | 0.10.2 |

每次训练前调用 `utils.set_seed(seed)`：固定 `random`、`numpy`、`torch` 与 CUDA 的随机种子，并设 `cudnn.deterministic = True`、`cudnn.benchmark = False`。相同的软硬件环境下同一 seed 可复现；更换 GPU 型号或 cuDNN 版本后仍可能出现数值差异。

代码默认**离线加载** `bert-base-chinese`（`HF_HUB_OFFLINE=1`），运行前需确保模型已在本地 Hugging Face 缓存中：

```bash
python -c "from transformers import AutoTokenizer; AutoTokenizer.from_pretrained('bert-base-chinese')"
```

### 6.2 配置文件

`configs/params.json` 已固定为交付配置，无需改动：

```json
{
  "model_name": "bert-base-chinese",
  "max_length": 128,
  "batch_size": 16,
  "lr": 2e-5,
  "max_epochs": 10,
  "patience": 3,
  "seed_list": [42, 66, 99],
  "dropout": 0.1,
  "max_norm": 1.0,
  "warmup_ratio": 0.1
}
```

### 6.3 运行

```bash
python main.py
```

一次运行依次完成 `[42, 66, 99]` 三个种子的训练。每个种子：

1. 建 SwanLab run，命名 `seed{seed}_lr{lr}_bs{bs}_dp{dp}`；
2. 训练 + 每轮验证，按 dev Acc 保存 `outputs/best_bert_seed{seed}.pth`；
3. 加载最优权重评估测试集；
4. 全部结束后打印 `mean ± std` 汇总。

预期输出：

```
当前设备：cuda
训练集: 3000 条 | 验证集: 1000 条 | 测试集: 1064 条
全局汇总自动检测到 15 个类别。
...
Epoch 7 | Train Loss: 0.0490 | Dev Acc: 83.20% | Dev Macro-F1: 81.96% | Dev Micro-F1: 83.20%
seed42 表现更好，保存 checkpoint (Acc: 83.20%)
...
  全部种子实验最终汇总结果
平均 Test Acc:        83.08% ± 0.28%
平均 Test Macro-F1:   81.98% ± 0.15%
```

### 6.4 复现实验矩阵

改 `configs/params.json` 的对应字段即可，一次只改一项：

```bash
# G1: dropout
#   0.1 → 0.2（初始基线）→ 0.3 → 0.4，其余不动
# G2: 学习率
#   1e-5 / 2e-5 / 3e-5，bs=16, dp=0.1
# G3: batch size
#   8，lr=2e-5, dp=0.1
```

每组 3 个种子约需 8–12 min；21 次运行全量约 1 h。

### 6.5 已知问题

|                       现象                       |                              原因                               |                          处理                           |
| ------------------------------------------------ | --------------------------------------------------------------- | ------------------------------------------------------- |
| `OSError: We couldn't connect to huggingface.co` | 代码强制离线                                                    | 先把模型缓存到本地，或临时去掉 `HF_HUB_OFFLINE`         |
| `CUDA out of memory`                             | bs 过大 / 序列过长                                              | 保持 `bs=16, max_length=128`；需要更大 batch 用梯度累积 |
| SwanLab 上传失败但训练继续                       | 网络问题                                                        | 本地 `swanlog/` 仍完整，事后可离线解析                  |
| checkpoint 单文件 1.17 GB                        | 同时保存了 optimizer 状态                                       | 仅推理时可只存 `model_state_dict`（约 390 MB）          |
| `swanlab watch` 读不到旧日志                     | 0.10 的本地看板只认 `runs.swanlab`，旧版离线 `run-*` 目录不兼容 | 用云端看板查看，或写脚本直接解析 `run-*/run-*.swanlab`  |

> **安全提示**：`main.py` 当前把 SwanLab API Key 内联在源码里，这是历史遗留写法。推送到公开仓库前应改为从环境变量读取（`os.environ["SWANLAB_API_KEY"]`），并作废已泄露的 Key。本 README 不记录任何密钥。
